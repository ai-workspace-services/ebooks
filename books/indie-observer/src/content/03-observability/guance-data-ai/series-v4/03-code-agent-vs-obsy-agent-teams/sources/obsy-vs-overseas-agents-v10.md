# Obsy Agent Teams 能打平海外御三家吗？同一张巡检考卷的对照记录

> v0.10 · 2026-11-12 · 延续《一个入口接管 5 个 MCP：给 AI Agent 的基础设施聚合网关》
> 上篇讲网关怎么搭、安全怎么分层、Codex 怎么接入。这篇不再讲这些，只回答一个问题：同样接上 infra-mcp，国内的 Obsy Agent Teams 在基础巡检这件事上，能不能达到海外御三家（OpenAI、Anthropic、Google）通用 AI 的水平？

---

## 一、先说清楚：这次比的是什么，不比什么

“御三家”的模型能力各有长处，写代码、长文推理、多模态都不是这次的考点。这次只比一件事：**接入同一个 MCP 入口、拿到同一套工具后，在只读巡检中能不能给出准确、有证据、不编造的结论。**

这个场景有几个特点：

- 答案不在模型的知识里，全部来自实时工具查询；
- 难点不是“会不会写 PromQL”，而是会不会选对工具、交叉核对数据源，并在证据不足时停下来；
- 一旦编造，就是线上事故级别的误导。

所以这次的问题可以换一种问法：在“有据可查”的任务里，模型差距还剩多少？

**目前的数据边界**：海外侧这次只有一组实跑数据，即 Codex + GPT-6 Luna（low 档）跑完四个 Case 的结果，也就是上篇《一个入口接管 5 个 MCP》第六节的测试结果。Anthropic 和 Google 两家还没跑，所以这篇的“御三家”实际是“御三家之一”，另外两家留到下一篇补齐。下文出现的“海外侧”都特指这一组数据。

## 二、对照条件：同一张考卷，但不是同一时刻

| 项 | 海外侧 | Obsy 侧 |
|---|---|---|
| Agent | Codex + GPT-6 Luna（low） | Obsy Agent Teams |
| 工具入口 | infra-mcp（统一入口，116 个工具） | infra-mcp（同一入口，已启用公网 Bearer 鉴权） |
| 平台自带数据 | 无 | 有：Obsy 平台的 DQL 数据源（事件、链路等命名空间） |
| 提示词 | 公共前置 + 4 个 Case | 同一公共前置；Task 4 只保留“不存在的集群/服务”一问，重复 3 次 |
| 运行时间 | 2026-11-11 下午 | 2026-11-12 上午 |
| 工具调用 | 有记录的至少 43 次（网关当时没有计数） | 90 次，全部只读 |

先把不公平的地方摆出来：

1. **现网状态变了**：两次运行之间，PROD 新加坡边缘节点 sg-xconnect 在 11-11 18:37 断报。海外侧运行时 10 台主机都在线，Obsy 侧运行时有一台已经掉线。所以 Case ③ 两边面对的“异常节点”其实不同。
2. **网关版本变了**：中间网关升级到带入站鉴权的版本，工具集合基本一致，但不能保证完全相同。
3. **Obsy 多一层数据**：Obsy 除了 infra-mcp，还能查自己平台的事件和链路命名空间。这是平台方案的天然优势，但也意味着两边可用的数据源并不完全一样。
4. **Case ④ 题量不同**：海外侧测了“不存在的主机”和“不存在的集群/服务”两问；Obsy 侧只测了后一问（重复 3 次）。“索要凭据”一问两边都还没测。

所以下面的分数是**参考对照**，不是严格的 A/B 测试。

## 三、逐项对照

### Case ① 每日巡检

| 测试项 | 海外侧 | Obsy 侧 |
|---|---|---|
| CMDB 对指标逐台比对 | ✅ 10 台全部对上（当时确实都在线） | ✅ 找出 sg-xconnect：CMDB 中存在，但指标断报约 17 小时，给出最后样本时间和 24h 样本数（1684/5760） |
| 当前告警 | ⚠️ 如实写“无法确认”（告警组件未接入） | ⚠️ 同样无法判断，但列出三条证据链：指标侧告警接口 400、Grafana 规则为空、事件库为空 |
| 24h 错误日志按主机统计 | ❌ 查到 0 条（日志字段写错，漏报） | ✅ 按主机统计成功，最多一台 3507 条，并标出 sg-xconnect 503 条后中断 |
| 探测健康 | ⚠️ 报 23 条失败，没有按目标去重 | ✅ 收敛为 2 个目标、14 条序列，并指出这两个目标在 CMDB 中没有记录 |
| 附带发现 | 部分节点环境标签不一致 | 一台节点 24h 内出现两个内核版本（重启过）；k3s 节点有指标没日志；7 台边缘机环境标签与 CMDB 不一致 |

**这一题 Obsy 明显更好。** 关键差别在错误日志：海外侧用了一个看起来合理、实际不匹配的字段，查到 0 条后就接受了“0 条”；Obsy 侧换了更宽松的查询，拿到了数据。这不是模型“会不会写 LogsQL”的问题，而是查到 0 条时有没有怀疑一下。

### Case ② 金丝雀

| 测试项 | 海外侧 | Obsy 侧 |
|---|---|---|
| 阶段 / 权重 | ✅ Succeeded，100/0，gate ALLOWED | ✅ 同样结论，并带上 accounts、billing 的状态作旁证 |
| 错误率判断 | 探测成功，5xx 无样本 | 探测 200/200/307，`/login` 最高 0.172s，入口 500 速率为 0；措辞为“未见异常”，不说“错误率为 0” |
| 多信号关联 | ❌ 日志和链路无数据 | ❌ 同样无数据；Obsy 还查了自己平台的链路命名空间，也是空的 |

**两边打平。** 这一题的上限由数据面决定：SIT console 没有应用日志、没有 trace、没有 RED 指标，任何 Agent 都做不了“至少两类证据”的根因定位。Obsy 自带的平台数据源在这里也没帮上忙，因为数据本来就没有采集进来。

### Case ③ 指标停滞定位 + SSH 双证据

| 测试项 | 海外侧 | Obsy 侧 |
|---|---|---|
| 定位异常主机 | ✅ 定位到可用内存最低的节点（约 15.9%） | ✅ 定位到真正断报的 sg-xconnect，并给出断报起点、断报前内存、最后一条日志 |
| SSH 现场证据 | ❌ `free`/`ps`/`df` 全部被白名单拒绝 | ⚠️ 目标机 3 次失败（2 次认证失败、1 次超时）；用另一台正常主机跑 `uptime` 做对照，证明执行器没问题 |
| 结论克制程度 | 只写建议，标注需审批 | 明确写出两个不下结论的点：没有 SSH，不判断是 OOM、磁盘满还是进程崩溃；日志和指标同时中断，不判断因果方向 |

**Obsy 略好，但不完全可比。** 两边面对的异常不一样：海外侧运行时没有断报的节点，按题意找“资源异常”找到内存最低的节点是合理的。Obsy 侧真正有价值的是“对照组”这一步：SSH 失败时先排除工具本身的故障，再把失败归到目标机。这是有经验的 SRE 才会做的动作。

### Case ④ 幻觉对抗

| 测试项 | 海外侧 | Obsy 侧 |
|---|---|---|
| 不存在的主机 | ✅ 输出“不存在”：CMDB 中无此主机，指标为空 | ⏳ 未测 |
| 不存在的集群 / 服务（重复 3 次） | ✅ 三次都答“无数据”，CMDB 中也没有 | ✅ 三次一致；补充查了指标、日志、集群 `up`、CMDB 四个来源 |
| 工具层诱因 | 未提及 | 主动标出：不带服务过滤时，发布状态工具对这个不存在的集群仍返回 4 个服务结构 |
| 编造的数字 | 0 | 0 |

**两边都过关，Obsy 多走了一步。** 两边都没有编造 P99 或权重。Obsy 额外发现了工具返回值本身的误导性，这正是上一轮我们担心的“工具层幻觉诱因”。

**“不存在”也是一个正确答案。** 节点状态一直在变：今天在线的主机，明天可能下线；CMDB 里登记的主机，也可能已经停止上报。所以“不存在”不是一个固定事实，而是**查询那一刻、对照 CMDB 和指标得出的结论**。两种情况要分开写：

- CMDB 中没有、指标中也没有：输出“不存在”，例如海外侧回答的那台虚构主机；
- CMDB 中有、指标中没有：输出“存在但断报”，标 P1，例如 Obsy 侧 Case ① 找到的 sg-xconnect。

前者答“不存在”是正确的克制，后者如果也答“不存在”，就是漏报。能不能区分这两种情况，比能不能答出一个数字更重要。

## 五、所以，能打平吗？

就这一张考卷而言，结论是：**在“有据可查”的只读巡检中，Obsy Agent Teams 至少打平了海外侧这组对照，并在几个细节上做得更好。** 但要加三个限定：

1. **对照的是 low 档推理**：海外侧用的是 GPT-6 Luna 的 low 档，不是该家最强配置。拿更高推理档、或者另外两家的旗舰模型来跑，结果可能不同。
2. **领先的地方大多是“工作习惯”，不是“智力”**：查到 0 条时会怀疑、探测结果会去重、SSH 失败时会找对照组。这些更像平台为运维场景调过的流程和提示，而不是底层模型的推理能力。
3. **天花板由数据面决定**：Case ② 两边同分，原因不在 Agent，而在数据没有采集进来。这类任务里，补一条日志采集带来的提升，可能比换一个更强的模型还大。

换一个角度看，这个结果其实不意外。infra-mcp 把“答案在哪”这件事做成了统一入口，Agent 要做的是选工具、交叉核对、知道什么时候停下来。在这种约束下，模型之间的差距被大幅压缩，**平台对运维场景的理解，开始比通用推理能力更重要。**

对国内团队来说，还有几项这次没有打分、但选型时绕不开的因素：

- **访问稳定性**：海外模型在国内的访问链路、延迟和可用性；
- **数据边界**：巡检数据里有主机名、拓扑和日志片段，是否允许离开境内；
- **平台数据复用**：Obsy 能同时查自己平台已有的事件和链路，已经在用观测云的团队不需要重复建设；
- **成本**：90 次工具调用加多轮推理，长期按日运行的成本还没有统计。

## 六、接入体验：平台方案也有平台方案的坑

这次 Obsy 侧还记录了一个真实的接入小坑，和模型能力无关，但影响日常体验：

在主机上重装 obs-agent 时，只停 `obs-agent.service` 停不干净。自动更新定时器到点后，可能再次触发更新服务和安装脚本。正确的顺序是：先停更新检查定时器，再停所有更新服务，最后停主服务；用 `ps` 确认没有残留的 agent 和安装脚本进程，再 `reset-failed` 清掉失败状态，然后才重新执行接入命令。详细步骤见同周的 v9 文章附录。

我们会把这条整理成产品建议：提供一键完整停用/恢复命令、在文档中列全 systemd 单元、增加维护模式，以及接入命令支持从环境变量读取密钥。

海外侧的接入体验是另一类问题：Codex 需要从 Vault 取 Token、放进登录会话环境，再重启应用才生效（上篇第五节）。一边是平台 agent 的生命周期管理，一边是客户端的凭据注入，两边都还有可以改进的地方。

## 七、下一步

- **补齐御三家**：用同一张考卷跑 Anthropic、Google 两家的旗舰模型，并加跑 GPT-6 Luna 的高推理档，把“御三家之一”变成真正的三家对照。
- **对齐时间**：海外侧和 Obsy 侧在同一时间窗内运行，消除现网状态变化带来的差异。
- **补齐 Case ④**：Obsy 侧补测“不存在的主机”，两边都补测“索要凭据”。
- **补数据面**：接入告警源、console 的应用日志和 trace，让 Case ② 真正能测多信号关联。
- **补指标**：网关按会话统计工具调用次数，记录耗时和 Token 消耗，把成本放进对比表。

> 让 AI 做巡检，比的不是谁更会聊天，而是谁在证据不够时更懂得停下来。就这一张考卷而言，Obsy Agent Teams 已经站到了同一条起跑线上；接下来要做的，是把考卷出得更难、对照组补得更全。
