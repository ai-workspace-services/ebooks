### 第一个商品，竟然是“储物柜”

很多人以为云计算是从“租虚拟机”开始的。其实 AWS 第一个正式商用的云服务是 S3，2006 年 3 月上线，比 EC2 的公测还早了几个月（EC2 在 2006 年 8 月开始公测）。

S3 上线那天是 3 月 14 日，恰好是圆周率日。它的定价也朴素得惊人：每 GB 每月 15 美分，用多少付多少。

S3 卖的是什么？是一个无限大的储物柜。你把文件放进去，拿到一个地址；要用的时候，凭地址取出来。不用关心硬盘在哪台机器上，也不用担心硬盘满了——存储第一次变成了一个 API。

![图解：为什么 S3 是 AWS 第一个正式商用云服务](images/008-图解：为什么_S3_是_AWS_第一个正式商用云服务.jpg)

![一图详解：S3 为什么让存储变成 API](images/026-一图详解：S3_为什么让存储变成_API.jpg)

![一图详解-存储服务化-s3](images/018-一图详解-存储服务化-s3.jpg)

这个看起来朴素的储物柜，后来托起了数据湖、备份归档，乃至今天的 AI 训练语料。

它最了不起的承诺，是“不丢”。AWS 宣称 S3 的设计目标是 99.999999999% 的持久性，也就是业内常说的“11 个 9”。做到这一点的办法并不神秘：同一份数据被自动存成多份，放在不同的设备、不同的机房里，坏了一份就再补一份。你看到的是一个地址，背后是一整套不停在“巡逻补货”的系统。

当然，“不丢”不等于“永远能访问”。2017 年 2 月 28 日，S3 在美国东部（弗吉尼亚北部）区域出了一次大故障。根据 AWS 事后公开的说明，一位工程师在排查计费系统变慢的问题时，按既定手册执行了一条命令，本想移除少量服务器，却因为一个参数输错，移除了远多于预期的服务器，其中包括管理所有对象位置信息的索引子系统。S3 不得不整体重启，前后大约四个小时才完全恢复。

更戏剧性的是，许多依赖 S3 的服务也跟着出了问题，就连 AWS 用来报告健康状态的仪表盘，因为同样依赖 S3，一度没法正常更新。事后 AWS 修改了工具，让它删得更慢，并且不允许把任何子系统删到最低容量以下。

这次事故成了云时代的一堂公开课：越是被大家当成“地基”的服务，越要小心那一行看似平常的命令。

### 一支在开普敦的小队

EC2 的故事则有一段有趣的“异乡”经历。它的早期开发主要由南非开普敦的一支小团队完成，带头人是 Chris Pinkham。据团队成员回忆，开始时只有十几个人，机架还没买，他们就用办公室角落里的一摞笔记本电脑来“假装”一个数据中心的机架，反复试验原型。

2006 年 8 月 25 日，EC2 公测上线。一个在地球另一端的小办公室里搭起来的系统，后来成了全球云计算的地基之一。

### 从磁盘到对象存储

要理解 S3 有多“离经叛道”，得先看看它之前的存储长什么样。最早是插在服务器上的磁盘；后来有了 NAS，把文件放在网络另一端的共享盘上；再后来有了 SAN，用专用网络把一大堆磁盘连成存储池。块存储、文件存储、对象存储，三兄弟各管一摊。

如果把数据比作货物：块存储像一个个没贴标签的格子，速度快，适合数据库这类需要“随手改一小块”的场景；文件存储像带目录的文件柜，大家按路径找东西，适合共享办公；对象存储像一座巨大的仓库，每件货都有一张取件码，不讲究目录，只讲究存得多、取得到。

![一图详解：从磁盘、NAS、SAN 到对象存储](images/031-一图详解：从磁盘、NAS、SAN_到对象存储.jpg)

![图解：从块存储、文件存储到对象存储](images/037-图解：从块存储、文件存储到对象存储.jpg)

对象存储的厉害之处在于：它不再假装自己是一块硬盘或一个文件夹，而是直接用“对象 + 地址”的方式对外服务。于是数据终于不必绑死在某一台服务器上了。

不过，这里藏着整个云时代的一条暗线：**数据比计算更难移动。**一台虚拟机关掉、换个地方重开，几分钟的事；可几百 TB 的数据要搬家，带宽、时间和流量费，样样都是真金白银。计算可以“随叫随到”，数据却会越积越重，最后像地心引力一样，把应用和服务都吸在它身边。这也是后面混合云和云中立两章，反复绕不开的那块石头。

![图解：数据为什么不能再绑死在服务器上](images/015-图解：数据为什么不能再绑死在服务器上.jpg)

### 云服务，不只是 EC2

S3 之后，EC2 来了，然后是数据库、队列、负载均衡……一件件过去要采购、要安装、要运维的东西，都变成了控制台上的一个按钮。

![图解：云服务不是只是 EC2](images/010-图解：云服务不是只是_EC2.jpg)

![图解：云服务如何接管资源世界](images/011-图解：云服务如何接管资源世界.jpg)

![一图详解：AWS 为什么重新定义了基础设施](images/020-一图详解：AWS_为什么重新定义了基础设施.jpg)

AWS 为什么能重新定义基础设施？因为它把“资源池化”做到了极致：计算、存储、网络都放进一个大池子里，谁要用，调一个 API 就能领走一份。服务器不再是一台台机器，而是池子里的一勺水。

这里的关键词是 API。过去的 IT 服务，入口是一个人：你找管理员，他帮你开机器。云把入口换成了一段程序可以调用的接口。区别在于，人一天只能处理几十个请求，接口一秒钟就能处理成千上万个。更重要的是，接口可以被另一段程序调用——这就为后来的自动化、弹性伸缩和基础设施即代码，铺好了路。

### VPC：在云上画出自己的院子

存储和计算都上了云，网络怎么办？如果大家都挤在同一张大网里，谁也不放心。

2009 年，Amazon 推出 VPC（虚拟私有云），让每个用户在云上画出一块属于自己的“院子”：IP 怎么分、子网怎么划、谁能进出，都由你自己定。云上网络从此被重新定义。

### 网络也开始软件化

VPC 背后，是网络的一场静悄悄的革命。过去改一条网络规则，要有人去机房里改交换机配置；现在，网络可以用软件来定义。

这一思路有个专门的名字，叫 SDN（软件定义网络）。它把网络设备里“决定数据往哪走”的大脑抽出来，集中到一个控制器里，设备本身只负责照着规则转发。又一次，控制面和数据面被分开了——这个套路，你在这本书里已经见过好几回了。

SDN 的一个重要起点，是 2008 年 Nick McKeown 等人发表的 OpenFlow 论文：给交换机定义一张标准的“流表”接口，让外面的控制器来写规则。

![图解：网络如何开始软件化](images/013-图解：网络如何开始软件化.jpg)

![一图详解：网络为什么也开始软件化](images/032-一图详解：网络为什么也开始软件化.jpg)

为了让成千上万个“院子”在同一套物理网络上互不干扰，人们发明了 Overlay 网络：在原有的网络之上再铺一层虚拟的路。

老办法是 VLAN：给每个院子发一个编号。可 VLAN 的编号只有 12 位，扣掉保留值，能用的只有 4094 个——对一朵要装下成千上万个租户的云来说，远远不够。2014 年发布的 RFC 7348 定义了 VXLAN，把编号扩到 24 位，大约 1600 万个，再把二层网络的包裹进三层网络里传送。院子的门牌号，一下子多了几千倍。规模继续变大，云厂商又开始把网络功能交给专属硬件来处理。

### 集装箱的启示

讲到这里，不妨先插一段航运史。1956 年，美国人马尔科姆·麦克莱恩把装满货物的标准铁箱子直接吊上船，开启了集装箱运输。在那之前，码头工人要把一袋袋、一箱箱形状各异的货物手工搬上船，装卸一艘货轮常常要好几天。

集装箱本身并不高科技，它厉害在“标准”：不管里面装的是咖啡还是电视机，外面都是一样的尺寸，一样的挂钩。于是起重机、卡车、火车、货轮都可以围绕同一个箱子来设计，整条运输链的效率一下子提了上去。

云和后来的容器，走的正是这条路：先把千奇百怪的东西装进标准的“箱子”，再让所有工具围绕箱子工作。Docker 的标志是一头驮着集装箱的鲸鱼，并不是巧合。

### Linux 悄悄占领了地基

在这场云的盛宴里，有个配角其实是主角：Linux。

大多数云主机跑的都是 Linux。它免费、开放、可以随便改，正好适合云厂商大规模定制。从单机到云时代，Linux 一路完成了“统治”。

### cgroup 与 namespace：容器的两块基石

Linux 内核里有两样东西，在云时代越来越重要。

cgroup 负责“限量”：这个进程最多能用多少 CPU、多少内存。2008 年，cgroups 并入了 Linux 2.6.24，同年 LXC 出现。namespace 负责“隔离”：让一组进程以为自己看到的是一个独立的系统。一个管饭量，一个管视野，两者合起来，就成了后来容器的地基。

cgroups 最早由 Google 的工程师提出并贡献给内核，最初的名字叫“进程容器”。Google 自己的数据中心里，早就在大规模地用类似的办法把很多任务塞进同一批机器里。后来的 Borg 和 Kubernetes，都站在这块地基上。

![一图详解：cgroup 与 namespace 为什么开始抬头](images/021-一图详解：cgroup_与_namespace_为什么开始抬头.jpg)

![一图详解：cgroup 和 namespace 如何成为资源控制内核](images/022-一图详解：cgroup_和_namespace_如何成为资源控制内核.jpg)

2014 年，eBPF 作为新的系统调用进入内核，让人能在内核里安全地插入小程序，观察和控制系统的每一个细节。Linux 被推向了控制面的中心。

![一图详解：eBPF 为什么把 Linux 推向控制面中心](images/023-一图详解：eBPF_为什么把_Linux_推向控制面中心.jpg)

于是到了 2013 年 Docker 开源、2014 年 Kubernetes 开源、2015 年 CNCF 成立时，一切已经水到渠成：容器时代的底层转折，早就在内核里埋好了伏笔。2010 年发布的 OpenStack，则试图把同样的“云”带进企业自己的机房。

Docker 的亮相方式也很有意思。2013 年 3 月，在美国的 PyCon 大会上，Solomon Hykes 做了一个只有五分钟的闪电演讲，题目是《Linux 容器的未来》。容器技术早就存在，Docker 做的是把它包装得简单好用：一条命令打包，一条命令运行，在你电脑上能跑的，在服务器上也能跑。

“在我电脑上明明是好的”——这句开发者之间流传多年的无奈台词，从此有了一个正经的解法。

![容器时代的底层转折](images/014-容器时代的底层转折.jpg)

很多人以为云计算卖的是服务器。服务器只是货架上最显眼的那一格。真正被卖出去的，是一整套控制面：申请、分配、计量、回收，再加上权限和账单。资源一旦被池化，控制面就会开始接管供给——你点的是“创建实例”，平台背后调度的是宿主机、网络、磁盘副本和计费规则。

也可以换个角度看容器和虚拟机。虚拟机回答的是：“如何把一台服务器变成多台可管理的机器？”容器回答的是：“如何把一个应用变成可复制、可调度的标准件？”前者更靠近硬件，后者更靠近业务。所以容器没有淘汰虚拟机：大量容器至今仍跑在虚拟机之上。云厂商先用虚拟机把物理机切成可售卖的单元，再在上面跑容器和编排。隔离强度和交付效率，站在两层不同的楼。

### 资源不缺，为什么系统还会卡？

云上帝国建起来了，资源似乎取之不尽。可一个老问题冒了出来：资源明明不缺，为什么系统还是会卡？

![资源不缺，为什么系统还是会卡-封面2](images/039-资源不缺，为什么系统还是会卡-封面2.jpg)
