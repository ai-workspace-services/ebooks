### 一座座孤岛

上一章说到，系统越长越胖，最后变成一张谁也管不过来的网。人们驯服它的第一招，要从“服务器是孤岛”这件事讲起。

很长一段时间里，一个应用就配一台物理机：财务系统一台，邮件一台，网站又一台。每台机器都按自己的高峰来买，结果大部分时间都闲着，CPU 常常只用了很小一部分。机器之间也不互通有无——这台忙得冒烟，旁边那台却在发呆，调度碰到了物理边界。

![01-服务器曾经是一座座孤岛](images/001-01-服务器曾经是一座座孤岛.png)

![02-服务器是一座孤岛](images/003-02-服务器是一座孤岛.png)

![01-调度遇到物理边界](images/002-01-调度遇到物理边界.png)

想象一栋公寓楼，每户都自己装了一台大锅炉，冬天烧一烧，其他季节就放着积灰。虚拟化的想法很简单：能不能整栋楼只装一台大锅炉，按需分给每一户？

孤岛还有一个隐藏的代价：时间。每上线一个新系统，就要走一遍采购、上架、装系统的流程。业务等得起吗？很多时候等不起，于是有人偷偷把新应用塞到一台“看起来比较闲”的老机器上，结果两个应用互相打架，一个出问题，另一个也跟着倒霉。

人们需要的，是一种既能共享硬件、又能互不干扰的办法。

### 把一台机器切成好几块

虚拟化的答案是：在硬件和操作系统之间插入一层软件，让一台物理机“假装”成好几台。每台虚拟机都以为自己独占了 CPU、内存和硬盘，其实它们在共享同一套硬件。

这件事并不是新鲜事。早在 1972 年，IBM 就推出了商用的 VM/370，在大型机上跑多个虚拟机。1974 年，Popek 和 Goldberg 还写了一篇论文，总结出一台机器要“好虚拟化”需要满足的条件。

麻烦在于，后来统治机房的 x86 处理器，并不完全满足这些条件：有一些敏感指令，在虚拟机里执行时不会乖乖“报告”给 Hypervisor，于是没法用最简单的办法拦截。

1998 年成立的 VMware 想了个巧办法：在运行时把这些“不听话”的指令悄悄翻译成安全的指令，这就是二进制翻译。后来 Intel 和 AMD 也在芯片里加上了硬件辅助虚拟化（Intel VT-x、AMD-V），让这件事变得容易多了。老想法就这样在 x86 的年代迎来了大爆发。

![03-虚拟化把服务器切成逻辑资源](images/006-03-虚拟化把服务器切成逻辑资源.png)

![计算虚拟化](images/029-计算虚拟化.png)

一台服务器从此不再是一个“整体”，而是一块可以切片的资源。这是 IT 史上第一次，人们开始用“资源”而不是“机器”来思考。

### 两种 Hypervisor

Hypervisor 大致有两种住法。

一种直接住在硬件上，下面没有别的操作系统，叫“裸金属”型，也叫一型。VMware ESX、Xen 都属于这一类，它们像大楼的物业，直接管着整栋楼的水电。

另一种住在一个普通操作系统里面，像一个应用程序一样运行，叫二型。你在笔记本上装一个虚拟机软件，跑一个别的操作系统试试新东西，用的多半就是这一类。VMware 自己就两种都有：机房里的 ESXi 是一型，开发者桌面上的 Workstation 是二型。它更像一位二房东：先租下一套房，再分租出去。

KVM 的身份有点特别：它是 Linux 内核里的一个模块，装上之后，Linux 本身就变成了一型 Hypervisor。物业和房东，干脆合成了一个人。

### Hypervisor：新的“分饼人”

插进去的那层软件，叫 Hypervisor。你可以把它想成一位分饼人：CPU 时间怎么分，内存给谁多一点，谁的硬盘读写要排队——都由它说了算。

![03-Hypervisor成为新的资源仲裁者](images/005-03-Hypervisor成为新的资源仲裁者.png)

![04-Hypervisor 是新的资源仲裁者](images/007-04-Hypervisor_是新的资源仲裁者.png)

![一图详解：Hypervisor 不是为了虚拟，而是为了分资源](images/020-一图详解：Hypervisor_不是为了虚拟，而是为了分资源.png)

所以有一句话说得很到位：Hypervisor 不是为了“虚拟”而虚拟，而是为了**分资源**。谁掌握了分饼刀，谁就掌握了这台机器的控制权。

分饼也有分饼的学问。CPU 可以按时间片轮流分，像几个人轮流用一台打印机；内存可以“超卖”，因为很多虚拟机申请了一大块内存，实际上只用了一小部分，Hypervisor 可以悄悄把闲着的部分借给别人。超卖得好，一台机器能多装几位住户；超卖过头，大家同时用力时就会互相抢，谁都跑不快。

这就是为什么虚拟化时代的运维，第一次需要认真地做“容量规划”：不是看一台机器有多大，而是看一池子机器在高峰时能不能扛住。

### 利用率越高，系统越脆？

切开机器，最直接的好处是“省”：原来十台机器各自闲着，现在可以挤在两三台上。

可省钱有个反面。机器塞得越满，留给意外的余地就越小。一台宿主机上住着十几台虚拟机，平时相安无事；某天其中一台突然狂吃 CPU 或磁盘，邻居们就跟着一起变慢——行内管这叫“吵闹的邻居”。宿主机一旦宕机，倒下的也不是一个业务，而是一串。

这就像把公交车挤到满员：每个座位都没浪费，可一个急刹车，所有人都站不稳。

所以，利用率和稳定性从来是一对拔河的绳子。后面所有的调度、限额、超卖策略，说到底都是在回答同一个问题：绳子拉到哪里，刚刚好？

### 切开之后，多了四样本事

服务器被切开之后，多出来几样过去想都不敢想的能力：一台物理机可以跑很多业务，利用率上去了；虚拟机可以打包成一个文件，复制、备份变得容易；虚拟机能在不停机的情况下从一台物理机“搬家”到另一台；坏了一台物理机，上面的虚拟机可以在别处重新拉起。

这几样本事加起来，改变的不只是一台机器，而是整个数据中心的玩法：机房开始从“摆机器”变成“管资源池”。

其中最让人惊叹的，是“不停机搬家”。2003 年，VMware 推出了 VirtualCenter 和 VMotion，可以把一台正在运行的虚拟机，从一台物理服务器迁到另一台，应用几乎感觉不到。据当年的报道，早期演示用的是 Windows 自带的 3D 弹珠台游戏：游戏一边玩着，虚拟机一边搬家，观众根本看不出它是什么时候换了机器的。

它的原理说起来并不玄：先在后台把内存一页页复制到新机器上；复制期间被改动的页面再补一遍；最后只剩很少一点时，短暂暂停一下，把最后的状态和网络身份一起交接过去。就像搬家公司趁你上班时把东西一车车运走，等你晚上回来，只需要换一把钥匙。

从这一刻起，物理服务器第一次变成了“可以随时维修、随时更换”的零件，而不是一碰就要停业务的宝贝。

### 调度器，悄悄接管了世界

切出来的“小机器”多了，一个新角色就变得重要起来：调度器。

谁先用 CPU，谁后用；新虚拟机该放在哪台宿主机上；哪台机器太挤了，要把谁搬走——这些决定，以前靠管理员拍脑袋，后来交给了软件。

调度器像一位不睡觉的排班经理。它不生产资源，却决定资源归谁。谁掌握了排班表，谁就掌握了这座机房真正的秩序。

这个角色在后面的故事里会越来越大：从虚拟化平台，到云，再到 Kubernetes，每一次升级，本质上都是换了一位更聪明、管得更宽的排班经理。

### 一场路线之争：Xen、KVM、ESXi

有了 Hypervisor，接下来就是一场“谁来当分饼人”的竞赛。

VMware 在 2001 年推出 ESX，后来成了企业数据中心的老大哥。2003 年，开源的 Xen 发布首个公开版本，一度风光无限。

它出自剑桥大学的一个研究团队，同年在学术会议上发表的论文标题，就俏皮地叫《Xen 与虚拟化的艺术》。2007 年，KVM 被并入 Linux 2.6.20 内核，走的是另一条路：不另起炉灶，直接让 Linux 内核自己变成 Hypervisor。

KVM 最初由以色列创业公司 Qumranet 的 Avi Kivity 开发，2008 年，Red Hat 收购了 Qumranet。还有 OpenVZ 这类方案，干脆在操作系统层面做隔离。

![图解 Xen、KVM、OpenVZ、ESXi 的架构差异](images/017-图解_Xen、KVM、OpenVZ、ESXi_的架构差异.png)

![一图详解-虚拟化技术路线之争](images/018-一图详解-虚拟化技术路线之争.png)

![一图详解：Xen、KVM、OpenVZ 各自争的是什么](images/021-一图详解：Xen、KVM、OpenVZ_各自争的是什么.png)

几条路线争的，其实都是控制权：控制权放在独立的 Hypervisor 里，还是放进操作系统内核里？在 Linux 的世界里，KVM 后来居上，一个重要原因是它“住在 Linux 里”，跟着内核一起升级，生态天然就大；Xen 则一直需要单独维护一层 Hypervisor，在主流 Linux 发行版里的位置逐渐让给了 KVM。不过 Xen 并没有消失，它在云计算早期扮演过重要角色，至今仍有项目在用。

![一图详解：为什么 KVM 最终赢了 Xen](images/022-一图详解：为什么_KVM_最终赢了_Xen.png)

![一图详解：为什么 Xen 没能成为 Linux 虚拟化底座](images/023-一图详解：为什么_Xen_没能成为_Linux_虚拟化底座.png)

如果把这几条路再拆开看，它们争的东西其实不太一样。

Xen 争的是虚拟化控制层：在硬件和操作系统之间，放一个独立的“仲裁者”，统一切 CPU、内存和 IO。早期公有云里，不少人喜欢它的隔离边界清晰。代价是它长期站在 Linux 内核之外——内核怎么演进，它都得额外追赶。

KVM 争的是 Linux 内核底座：不另建王国，而是让 Linux 自己变成 Hypervisor。虚拟机在它眼里，更像普通进程。Linux 的调度、驱动、网络和工具链怎么升级，KVM 都能顺手接住。所以有人总结：Xen 早期赢在架构，KVM 长期赢在生态。

OpenVZ 争的是轻量隔离入口：不虚拟一整台机器，而是在同一个内核上切出多个环境。它常见于早期的廉价 VPS，密度高、成本低，也给后来的容器思路埋了伏笔——后人会说，容器时代并不是凭空冒出来的。

ESXi 争的是企业数据中心的管理入口：Hypervisor 之外，还有 vCenter、迁移、高可用、资源池一整套平台。它卖的不只是“能虚”，而是“能管”。

四条路线表面在比性能和隔离，深处比的是：**谁掌握资源入口，谁就掌握分配方式。**

### Linux 成了入口

KVM 的胜利，顺带让 Linux 成了虚拟化的入口：既然内核本身就能当分饼人，那么谁掌握了 Linux，谁就站在了虚拟化的大门口。这件事的影响会一直延续到云时代——下一章你会看到，Linux 几乎占领了整个云基座。

![06-Linux 为什么最终成了虚拟化入口](images/011-06-Linux_为什么最终成了虚拟化入口.png)

### 不止切 CPU：存储和网络也被切开

虚拟化不只发生在计算上。硬盘被抽象成了存储池，按需划给每台虚拟机；网络也被虚拟化，交换机和网卡可以用软件“画”出来。

![存储虚拟化演进](images/025-存储虚拟化演进.png)

![网络虚拟化演变](images/026-网络虚拟化演变.png)

计算、存储、网络三样都被抽象之后，“云”的原材料就算齐了。

网络虚拟化最直观的例子，是虚拟交换机：同一台物理机上的几十台虚拟机，彼此之间的通信根本不用出这台机器，由 Hypervisor 里的一台“软件交换机”转发。网络工程师第一次发现，自己要管的交换机，有一大半看不见、摸不着。

### 一条支线：从 chroot 到 Docker

在虚拟机之外，还有一条更轻的支线。1979 年 Version 7 Unix 引入了 chroot，2000 年 FreeBSD 有了 Jail，2005 年随 Solaris 10 正式发布的 Zones 把隔离做成了操作系统的标准功能，Linux 这边则有 Virtuozzo 和 2005 年开源的 OpenVZ。这些技术不去模拟整台机器，而是在同一个操作系统里，把应用彼此隔开。这条支线一路走到 2013 年开源的 Docker，隔离的对象从“机器”下沉到了“应用”。

![07另一条支线-从 chroot 到 Docker，隔离开始下沉到应用](images/013-07另一条支线-从_chroot_到_Docker，隔离开始下沉到应用.png)

容器和虚拟机的区别，可以用住房来比喻：虚拟机像独栋别墅，每家都有自己的地基、水电和围墙，最安全，但造价高、盖得慢；容器像公寓里的一套套房间，共用一栋楼的地基和管道，便宜、入住快，只是隔音没那么好。两种房子后来都没有消失，各有各的住户。

### 云的前夜，和 AI 的回马枪

到 2000 年代中期，资源池、虚拟机迁移、存储网络虚拟化都已就位。云平台的前夜到了。

![08 云平台的前夜已经到来](images/014-08_云平台的前夜已经到来.png)

故事还有一个有趣的回马枪。AI 时代的训练任务对 GPU 和网络极其挑剔，不少场景开始偏爱物理机，或者把虚拟化做得尽量“薄”。2017 年，AWS 推出 Nitro，把虚拟化的大部分工作下沉到专用硬件上。2023 年，博通完成对 VMware 的收购，许多企业也开始重新审视自己的虚拟化选型。

![AI与物理机](images/015-AI与物理机.png)

![AI时代的工作负载](images/016-AI时代的工作负载.png)

所以，虚拟化从来没有消失，它只是越来越靠近底层硬件，变成了一块大家看不见、却离不开的地板。
