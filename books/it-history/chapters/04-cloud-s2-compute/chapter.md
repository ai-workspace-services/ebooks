### 开机，不再需要填工单

上一章结尾留下一个问题：资源取之不尽，为什么系统还会卡、钱还会不够？要回答它，得先看看“开一台机器”这件事，在云上变成了什么样子。

以前在公司里要一台服务器，流程大概是：写申请、等审批、等采购、等上架、等装系统，几周过去了。2006 年 EC2 出现之后，这一切变成了一个 API 调用，几分钟就好。下面这组图，是 AWS 云服务的一次快速巡礼。

这件事的意义，远不止“快”。当开机器只需要几分钟、几块钱的时候，人们做事的方式就变了：想试一个新点子，不用先写预算报告，开几台机器试一下午，不行就关掉。很多后来的互联网公司，正是在这种“便宜地试错”的环境里长大的。

创业的门槛，第一次从“先买一屋子服务器”降到了“先有一张信用卡”。

### 一场三天的停摆

为什么大公司愿意把家当搬上云？Netflix 的故事很有代表性。

2008 年 8 月，那时 Netflix 还以邮寄 DVD 为主业。它的发货系统遭遇了一次严重的数据库损坏，前后大约三天没法正常给会员寄出光盘。事后排查，罪魁祸首是一个出了故障却没有报出任何错误的硬件部件。

Netflix 后来回忆说，正是这次事故让他们下定决心：不能再依赖机房里那种“一台大数据库扛所有”的单点，而要转向云上可以横向扩展的分布式系统。他们选了 AWS，花了七年时间，到 2016 年初才把流媒体服务的最后一点机房家当搬完。

### IaaS：把机房打包成积木

EC2 代表的这一类服务，叫 IaaS（基础设施即服务）。它抽象掉的是机房里最“重”的那部分：机柜、电源、网线、硬盘。计算、网络、存储三样整合在一起，就诞生了 IaaS 云服务。

![图解：IaaS 抽象了什么](images/028-图解：IaaS_抽象了什么.jpg)

![计算、网络、存储的整合，诞生了 IaaS 云服务](images/082-计算、网络、存储的整合，诞生了_IaaS_云服务.jpg)

![物理资源池-云平台](images/081-物理资源池-云平台.jpg)

最直观的变化是：资源 API 替代了工单。你不用再找人，代码就能开机、关机、挂硬盘。云平台也就此接管了资源的“控制面”。

“控制面”这个词后面会反复出现，这里先把它讲清楚。你可以把一套系统分成两层：一层是真正干活的，比如跑应用的机器、传数据的网络，叫“数据面”；另一层是发号施令的，决定开几台机器、谁能访问什么、出了问题怎么处理，叫“控制面”。

打个比方，数据面是马路上跑的车，控制面是红绿灯和交通指挥中心。IaaS 让企业第一次可以通过一个 API，去操纵一个巨大的交通指挥中心——只不过，这个指挥中心的主人是云厂商。

### OpenStack：在自家机房里造一朵云

公有云这么好用，企业自然想：能不能在自己机房里也来一套？2010 年发布的 OpenStack 就是这个想法的代表。它把云拆成一个个组件：Nova 管计算，Neutron 管网络，Cinder 管块存储……拼在一起，就是一台云主机背后的整套机器。

![一台云主机背后的 OpenStack 组件](images/051-一台云主机背后的_OpenStack_组件.jpg)

![图解：Nova、Neutron、Cinder 如何拼成云](images/032-图解：Nova、Neutron、Cinder_如何拼成云.jpg)

OpenStack 是私有云绕不开的一站，但它也出了名地难做：组件多、版本多、运维门槛高，很多团队搭得起来，却养不太好。

OpenStack 最初由 Rackspace 和美国航空航天局（NASA）在 2010 年联合发起，一度是开源世界里最热闹的项目之一，几乎所有大厂商都派人参与。热闹的另一面是复杂：每个厂商都想把自己的需求加进去，组件越加越多，一套完整的部署往往需要一个专门的团队来照料。

这段经历给后来者上了一课：开源项目的成败，不只看功能多少，还要看“养得起”。几年后 Kubernetes 能后来居上，一个原因就是它的核心更小、边界更清楚。

### 弹性：像水龙头一样开关

弹性听起来像“多买几台机器”，其实更像控制供给的节奏：高峰时拧大，低谷时拧小。传统机房往往按峰值采购，结果大半时间在养闲置容量；弹性计算把固定资产，变成了可以开关的流动能力。

监控、调度、负载均衡和健康检查一起上场之后，自动伸缩才站得住脚。业务侧看到的是“实例变多了”，平台侧看到的是“哪个资源池还有余量、哪台宿主机更合适、账单怎么记”。

云最迷人的地方是弹性。2009 年，EC2 有了 Auto Scaling：流量涨了自动加机器，流量落了自动减。容量计划也从“一年做一次”变成了“随时在变”。

![图解：Auto Scaling](images/026-图解：Auto_Scaling.jpg)

![一图详解：云平台弹性](images/064-一图详解：云平台弹性.jpg)

![图解：容量计划动态化](images/041-图解：容量计划动态化.jpg)

可弹性是一把双刃剑。按量计费改变了成本结构——不用一次掏大钱买机器了，但每个月的账单像天气预报，说不准会下多大的雨。弹性越强，预算焦虑也被放得越大。给资源打标签、按团队分账，成了新的必修课。

为什么账单会失控？原因往往很平常：测试环境开了忘了关；为了排查问题打开了详细日志，事后没有收回；一个程序出了 bug，在半夜里不停地自动扩容。在机房时代，这些失误最多浪费一点电；在云上，它们会一分不差地出现在月底的账单上。

所以有人说，云把“技术问题”变成了“财务问题”，也把“财务问题”变回了“技术问题”：想省钱，得先看懂每一行资源从哪里来。

### PaaS：开发者只管写代码

IaaS 往上再走一步，是 PaaS（平台即服务）。2007 年的 Heroku、2008 年的 Google App Engine 都是先行者。在这里，开发者连操作系统都不用管，只要把代码推上去，平台负责运行、扩容和打补丁。

![图解：为什么说 PaaS 解放了开发者](images/036-图解：为什么说_PaaS_解放了开发者.jpg)

![去编号_PaaS解放开发者_1](images/076-去编号_PaaS解放开发者_1.jpg)

这背后有一个趋势：业务应用越来越标准化。既然大家的应用都长得差不多，那么运行它们的平台，也就可以做成通用的。

Heroku 当年最让开发者着迷的，是一条命令：把代码用 git 推送到平台上，应用就上线了。不用申请服务器，不用装数据库驱动，不用配负载均衡。对很多小团队来说，这是第一次感觉到“运维可以不是自己的事”。

PaaS 的代价是自由度：平台替你做了很多决定，你就得按平台的规矩来。语言版本、运行时长、能装什么软件，都有边界。这个取舍，后来在 Serverless 身上又被放大了一次。

![业务 APP 越来越标准化](images/075-业务_APP_越来越标准化.jpg)

### 容器和虚拟机，到底隔离了什么？

在 IaaS 和 PaaS 之间，容器悄悄长成了主力。

为什么是容器？因为它刚好卡在一个舒服的位置：比虚拟机轻，比 PaaS 自由。你可以把应用连同它依赖的所有东西打包成一个镜像，镜像在哪里都能一模一样地运行；同时，你仍然可以自己决定用什么语言、装什么软件。开发者既不必向平台低头，也不必再操心服务器。

虚拟机隔离的是一整台“机器”，自带操作系统，所以更重、启动更慢，但隔离更强；容器只隔离“进程”，共享宿主机内核，所以又轻又快，但隔离相对弱一些。隔离强度和启动速度，很难两全其美。

![图解：为什么容器启动比 VM 快？](images/035-图解：为什么容器启动比_VM_快？.jpg)

![图解：容器到底隔离了什么？](images/040-图解：容器到底隔离了什么？.jpg)

![一图看懂：容器和虚拟机到底隔离了什么](images/056-一图看懂：容器和虚拟机到底隔离了什么.jpg)

![一图看懂：隔离强度与启动速度为什么不可兼得](images/058-一图看懂：隔离强度与启动速度为什么不可兼得.jpg)

容器的底座，正是上一章说到的 namespace 和 cgroups。

所以容器并不是一种“新的机器”，它只是一个被内核特别照顾的普通进程：namespace 给它戴上一副眼罩，让它只看得见自己的文件和网络；cgroups 给它套上一个饭盒，规定它最多能吃多少。摘掉眼罩和饭盒，它和宿主机上的其他程序没有什么两样。

明白了这一点，就明白了容器为什么启动得快——它不需要“开机”，只需要“开一个进程”。

![一图看懂：Namespace 与 Cgroups 为什么是容器底座](images/052-一图看懂：Namespace_与_Cgroups_为什么是容器底座.jpg)

调度对象也随之变了：从调度一台台虚拟机，变成调度成百上千个容器，控制权进一步上移。

![一图看懂：VM调度-容器调度差异](images/054-一图看懂：VM调度-容器调度差异.jpg)

![一图看懂：从 VM 调度到容器调度，控制权](images/055-一图看懂：从_VM_调度到容器调度，控制权.jpg)

这也是为什么容器兴起之后，虚拟机并没有退出公有云货架。云服务器仍然是最好理解、最好计费、最好交付的基础商品：vCPU、内存、磁盘、带宽，边界清楚。容器改变的是应用怎么打包和调度，不是把“机器级隔离”这件事取消掉。两个楼层，各干各的。

### Pod 与 Kubernetes：给容器配一个“班长”

容器多了，总得有人管。Kubernetes 的答案是 Pod：把几个关系紧密的容器装进一个小组，同进同出，共享网络和存储。Pod 本身，也是一种资源抽象。

![一图看懂：Pod 为什么也是一种资源抽象](images/053-一图看懂：Pod_为什么也是一种资源抽象.jpg)

![一图详解：为什么还要再抽象出 Pod](images/063-一图详解：为什么还要再抽象出_Pod.jpg)

Kubernetes 源自 Google 内部多年的集群管理经验，2014 年开源，2015 年发布 1.0。它的控制面就像一个永不睡觉的班长：你告诉它“我想要 3 个副本”，它就一直盯着，少了补上，坏了重建。

Google 内部那套前辈系统叫 Borg，2015 年 Google 才发表论文公开它的细节。Kubernetes 这个名字来自希腊语，意思是“舵手”，所以它的标志是一个船舵。舵上有七根辐条，据创始团队的说法，这是因为项目最初的内部代号叫“Seven of Nine”——《星际迷航》里一个从 Borg 集体中被解放出来的角色。一个从 Borg 里走出来的开源项目，用这个梗再合适不过。

这种“你说想要什么，我负责一直保持”的方式，叫声明式管理。它和“先做这个、再做那个”的命令式脚本很不一样：脚本执行完就结束了，控制器却一直在循环比对“期望”和“现实”，发现不一致就动手修正。这个小小的思路转变，后来成了 GitOps、平台工程的地基。

### 为什么最后是 Kubernetes？

Kubernetes 不是凭空长出来的。在它之前，Google 内部走过了两代：前面提过的 Borg，早在 Kubernetes 之前就管着 Google 的生产集群；2013 年，Google 又发表了 Omega 的论文，尝试让多个调度器共享一份集群状态、并行做决定。Omega 的不少想法后来回流进了 Borg，也流进了 Kubernetes。三代系统，一条线。

Kubernetes 也不是唯一的选手。2009 年，加州大学伯克利分校的几位研究者做出了 Mesos 的前身，2013 年它成为 Apache 顶级项目，一度是大规模集群管理的热门选择；2016 年，Docker 1.12 把 Swarm 模式直接装进了引擎，主打“开箱即用”。

可几年之后，牌局已经很清楚。2019 年，Docker 把企业业务卖给了 Mirantis；2025 年，Apache Mesos 因为长期不活跃，被投票移入 Apache Attic——也就是开源项目的“退休之家”。

输的一方并不是技术不好。Mesos 更像一个通用的资源分配底座，上面还得再搭框架；Swarm 简单好用，但生态始终没长起来。Kubernetes 赢在把“声明式 API + 控制器”做成了一套人人都能往上扩展的标准，又有中立的基金会托管，云厂商们都愿意上桌。

赢下的不是一个调度器，而是一个标准。

### Serverless：把服务器藏到最深处

再往上走一步，就到了 Serverless。2014 年 11 月，AWS 在 re:Invent 大会上推出了 Lambda 函数计算：你只写一段函数，什么时候触发、跑在哪台机器上、要多少台，统统交给云。

![为什么 Serverless 会诞生](images/023-为什么_Serverless_会诞生.jpg)

![从服务时代到事件时代](images/025-从服务时代到事件时代.jpg)

![图解：函数计算与事件驱动](images/038-图解：函数计算与事件驱动.jpg)

服务器并没有消失，只是被藏到了最深处。世界也从“服务时代”走向了“事件时代”——不是一直开着等请求，而是事件来了才醒过来干活。

事件驱动最常见的例子，是上传一张图片后自动生成缩略图：图片一落进存储，就触发一个函数，函数把缩略图做好、存回去，然后休息。没有图片上传时，它一分钱不花。

代价是“冷启动”：一个很久没被叫醒的函数，第一次被调用时需要先准备运行环境，响应会慢上一拍。就像一家只在有客人时才开灯烧水的小店，省了电费，但第一位客人得多等一会儿。

![一图详解：Serverless 藏起服务器](images/061-一图详解：Serverless_藏起服务器.jpg)

![去编号_Serverless藏到最深处](images/077-去编号_Serverless藏到最深处.jpg)

但 Serverless 也是厂商绑定最极端的形态：函数写得越多，越离不开这朵云。运维的工作也随之变化，从管机器，变成了管配置、管权限、管账单。

![Serverless 是厂商绑定的极端形态](images/049-Serverless_是厂商绑定的极端形态.jpg)

![IT简史：Serverless与运维变化](images/011-IT简史：Serverless与运维变化.jpg)

弹性把预算问题也拉进了控制面。资源越容易创建，浪费也越容易发生。于是资源标签、成本中心、预算告警这些不起眼的东西，渐渐变成了治理入口：没有标签，账单会变成一锅粥；有了标签，才谈得上谁用了多少、该不该关掉。弹性放大了能力，也放大了“算不清楚账”的焦虑。

### 控制权一路上移

把 IaaS、PaaS、Serverless 排成一排，你会看到一条清晰的线：每往上走一层，用户就少管一点，云就多管一点。弹性计算的本质，就是控制权上移。

![一图详解：从 IaaS 到 Serverless，谁在控制资源](images/067-一图详解：从_IaaS_到_Serverless，谁在控制资源.jpg)

![去编号_弹性计算控制权上移](images/078-去编号_弹性计算控制权上移.jpg)

于是一个新的担心浮出水面：企业怕的其实不是上云，而是失控。

失控的感觉，往往来自三件事：看不清——资源散落在几十个账号里，没人说得清总共有多少；管不住——每个团队都能随手开资源，规则形同虚设；退不出——业务和某朵云的专有服务缠得太紧，想换都换不了。

这三件事，恰好对应了后面三章的主题：混合云与治理、自动化与平台工程、开源与云中立。

![IT简史：图解企业控制权](images/013-IT简史：图解企业控制权.jpg)

### 消失的中台，和换了算法的账本

控制权上移，还悄悄吞掉了一样东西：中台。

2015 年 12 月，阿里巴巴提出“大中台、小前台”，把搜索、共享业务、数据技术这些公共能力收进中台，让前台业务轻装快跑。此后几年，“建中台”在国内企业里风靡一时。

可没过多久，不少企业发现，自己辛苦搭的许多中台能力——用户、消息、数据管道、监控——云平台上已经有现成的 PaaS 服务，而且更新得更快。不少企业开始重新掂量：哪些能力值得自建，哪些交给平台就好。这并不是说中台想法错了，而是“共享能力”这一层，被往下压到了平台里。

跟着变的，还有账本。过去建机房是 CapEx（资本支出）：一次性买服务器，分几年折旧，买多了闲着，买少了不够。云把它变成了 OpEx（运营支出）：用多少，付多少，按小时甚至按秒计费。

这看起来只是财务科目的变化，其实改的是决策方式：以前是“先买再用”，一次拍板、几年不变；现在是“边用边付”，每天都在花钱。门槛低了，账单也更容易失控——这正是后来 FinOps 登场的伏笔。

### 替代者们：PVE、Rancher、Harvester

一些替代方案走到了台前。Proxmox VE 在 2008 年 4 月发布首个公开版本，最初把 KVM 虚拟机和 OpenVZ 容器放进同一个网页界面里管理；后来容器换成了 LXC（2015 年的 4.0 版），又集成了 Ceph 分布式存储。今天的 PVE 把 KVM、LXC、Ceph 组合成私有云底座，成了不少团队的补位选择。

![PVE 为什么成为私有云的补位选择](images/017-PVE_为什么成为私有云的补位选择.jpg)

另一条路是让 Kubernetes 反过来接管私有云：SUSE Rancher 把 Kubernetes 带进企业机房，2021 年 GA 的 Harvester 1.0 则试图把虚拟机和容器融合在同一个平台上，让 Pod 网络也能接入虚拟机。

这条路的思路很有意思：过去是“在虚拟机上跑容器”，现在反过来，“在容器平台上跑虚拟机”。既然 Kubernetes 已经成了大家最熟悉的控制面，那就让它把虚拟机也一起管起来。新旧两种工作负载，第一次可以用同一套工具、同一套流程来对待。

### 开源，不等于便宜

最后要算一笔容易被忽视的账：省了授权费，真的就省钱了吗？

开源软件不收许可费，但需要人去搭、去维护、去升级。技术成本和商业成本是两回事；生态的成熟度，常常决定了一个私有云项目的成败。低成本私有云也有它的边界：控制权很贵，私有云同样如此。

有一个简单的算法可以帮你判断：把“省下的授权费”和“多出来的人力、学习和风险成本”放在一起比。如果团队里没有人真正懂这套系统，出了问题只能干等社区回复，那么省下来的钱，可能会在第一次重大故障时一次性还回去。

这并不是说开源不好。恰恰相反，下一章、再下一章，我们都会看到开源的价值。只是要记住：开源省掉的是“买”的钱，省不掉“养”的钱。
